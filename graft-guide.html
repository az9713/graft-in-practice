Graft, and how to actually use it in Claude Code

Graft builds a map of your codebase once and hands it to your coding agent, so the agent stops re-exploring the same repo on every task. This page says what it is, what it does under the hood, and gives worked examples you can copy.

1. The problem it solves

You ask Claude Code to change the auth flow. Claude does not know where auth lives. So it greps a word, reads a file, follows an import, backs out, greps again. Each of those steps lands in the conversation, and every later model call resends the whole conversation. You pay for that search three ways: tokens, tool calls, and wall-clock time. Then the session ends and everything Claude learned is thrown away. The next task starts from zero again.

A human joins a codebase once. An agent joins it every single time you press enter.

Graft's answer is to do the exploring once, up front, and save the result as files in the repo. The agent reads the map instead of rebuilding it.

2. What Graft builds

Graft writes one folder, graft/, at the root of your repo. It holds two different maps of the same code.

The wiring graph

freeno API keyoffline

Every function, class, method and type in the repo, plus the edges between them: who calls what, who imports what, who implements what. Built by tree-sitter, a real parser. It is deterministic — same code in, same graph out. No model is involved at any point.

Lives in graft/.graph/wiring.json plus one small card per source file.

The concept nodes

needs an LLM keyopt-in

Markdown files, one per subsystem or idea, each written in plain English: what this part does and how it connects to the rest. Links between nodes are [[wikilinks]] with typed verbs like depends_on, uses, produces.

Only built when you run graft build --deep with a provider key. Nothing builds these behind your back.

The important split. Everything Claude Code does with Graft day to day — ask, grep, skeleton, callers, map, blast — runs on the free wiring graph. You never need an API key to get value from this. The --deep layer is an extra, and it is the only part that costs money.

graft build adds graft/ to your .gitignore by itself. The graph is a local cache, like node_modules. You do not commit it. What you commit is the small wiring in .claude/, and each teammate runs graft build to make their own copy.

3. How it works

The build

Graft walks the files Git can see, parses each one with tree-sitter, and writes out the symbols and the edges. Here is a real cold build of the Graft source tree itself, 265 files:

$ graft build .
✓ wiring: 2038 nodes (1353 function, 265 file, 236 interface, 109 method, 47 type, 28 class),
  6082 edges, 265 cards [javascript, typescript]
  parsed: 265 of 265 files (0 replayed from cache)

real    0m10.262s

Ten seconds, no key, no network. Every file is cached by a hash of its content. Run it again with nothing changed:

$ graft build .
  parsed: 0 of 265 files (265 replayed from cache)

real    0m2.052s

Why that cheapness matters

Because a rebuild is nearly free, Graft can refresh before it answers every single query. When you run graft ask, it first checks the file sizes and timestamps against the last build's fingerprint. That check takes a few milliseconds. If nothing moved, it answers straight away. If something moved, it re-parses only what moved, then answers.

The practical result: the answer describes your code as it is right now, including edits you have not saved to Git. Uncommitted, unstaged, staged — all the same to Graft. There is no stale index to remember to rebuild.

Turn the refresh off per command with --no-refresh, or everywhere with GRAFT_NO_REFRESH=1.

Where the money goes

ThingRuns whereCosts
graft build, graft checkyour machine, tree-sitter$0, no key, no network
ask grep skeleton callers map blastyour machine, reads the graph$0, no key, no network
graft build --deepyour LLM provideryour key, your model, your bill
graft blast --nameyour LLM providerone cached call to name the areas

For --deep you pick the provider. Set GRAFT_PROVIDER (openai for anything OpenAI-compatible, anthropic for the native API, or litellm / orcarouter for a gateway), plus GRAFT_API_KEY, GRAFT_MODEL, and GRAFT_BASE_URL when you are pointing at OpenRouter, Fireworks, Groq or a local server.

Languages

Twenty-three, at three levels of fidelity, all free and deterministic:

  • Full — hand-written extractors with cross-file call and import resolution: TypeScript / JavaScript (with JSX and TSX), Python, Go, Java, Kotlin, PHP, Swift, R.
  • Broad — symbols plus name-matched call edges via a generic extractor: Rust, C, C++, C#, Ruby, Scala, Elixir, Solidity, OCaml, Zig, Dart, Clojure, Nix, Lua.
  • Compiler-grade, opt-in — graft build --lsp adds precise edges when a language server is on your PATH: rust-analyzer, clangd, gopls, pyright, typescript-language-server. Best-effort; with no server installed the graph is unchanged.

A file in a language not on that list is skipped, not indexed.

4. How it plugs into Claude Code

One command does the wiring, per repo:

cd path/to/your/repo
graft init --dry-run --agents claude   # see what it would write, write nothing
graft init --agents claude             # actually do it

Here is the real dry-run output, so you know exactly what lands:

$ graft init . --dry-run --agents claude
would write — this repo:
  .claude\settings.json                 graft statusline + hook blocks
  .claude\helpers\graft-statusline.cjs  statusline shim
  .claude\helpers\graft-hooks.cjs       hooks shim
  .claude\skills\graft\SKILL.md         graft skill
  .mcp.json                             mcpServers.graft

nothing was written (--dry-run)

Five files. It never touches your CLAUDE.md. Re-running only refreshes Graft's own blocks and leaves the rest of your settings alone.

The skill file

.claude/skills/graft/SKILL.md is a normal Claude Code skill, generated for you. Its job is to tell Claude: this repo has a map, use it before you grep. It lists the six commands, says which one fits which task, and pushes hard on spending one call rather than four. If you have ever wondered what a good skill looks like, read this one — it is a tool writing its own instructions.

The hooks

A hook is a small script Claude Code runs by itself at a fixed moment. graft init installs five entries in .claude/settings.json:

EventWhat it doesBudget
SessionStartHands Claude the repo map when a session opens, so it starts oriented instead of blind.8s
UserPromptSubmitReads your prompt, finds the matching nodes, and attaches them. This is the main event — context arrives without you asking for it.15s
PostToolUse on Write|Edit|MultiEditAfter Claude edits a file, prints the blast radius inline — what depends on the thing that just changed — and re-syncs the graph.10s
PostToolUse on Bash|mcp__graft__|Read|Grep|GlobBookkeeping. Sums the "tokens saved" footers and counts graft reads against raw file reads, which is what the statusline shows.8s
StopAt the end of a turn that touched code, rebuilds the markdown cards in the background.8s

Every one of those is structural and free. The hooks never call an LLM on their own.

Two more things it writes into settings.json

  • A permissions allowlist. Bash(graft:*), Bash(npx graft:*), Bash(graft-dev:*), Bash(node dist/cli.js:*). Without it, a graft call in a headless or subagent run raises a permission prompt and loses to plain grep.
  • A footer link regex matching graft/…*.md, so node paths in Claude's output are clickable.

The statusline

Graph size, percent enriched, and a ⚠ N stale warning when the code has moved ahead of the graph, plus a running session total of tokens saved.

Statusline trap. This is a project-level statusLine, and a project-level one hides whatever you have in ~/.claude/settings.json. If you run a custom statusline, wire with graft init --agents claude --no-statusline (or set GRAFT_NO_STATUSLINE=1). Graft is careful in the other direction too: if a statusLine is already there and is not Graft's, it leaves it alone and prints a warning.

The MCP server

graft init also writes .mcp.json so the same six capabilities show up as native tools, no shell needed. Restart Claude Code to load it.

ToolTakesGives
graft_find_codea questionRanked hits with file:line and the source inlined.
graft_file_apia file pathEvery signature in that file, no bodies.
graft_trace_callsa symbolWho depends on it, or what it depends on, N levels deep.
graft_find_alla regexEvery hit, grouped by enclosing symbol.
graft_repo_mapnothingDirectory clusters, hubs, hotspots.
graft_check_freshnessnothingWhether the graph has drifted from the code.

Skip it with --no-mcp, or run the server by hand with graft mcp [dir].

6. Worked examples

These are things you type into Claude Code in a repo where graft init has run. In most of them you do not name Graft at all — the skill file and the hooks make Claude reach for it. The examples show what happens underneath so you can tell whether it worked.

Example 1 — Landing in a repo you have never seen

You:  Give me a map of this codebase. Main subsystems, and how a request
      gets from the HTTP layer to the database.

Without Graft: Claude runs ls, opens the README, greps for "router", reads three files, greps for "db", reads two more. Eight to twelve tool calls, most of a file's worth of tokens each.

With Graft: the SessionStart hook has already handed Claude the repo map. It runs graft map once for the hub list, then one graft ask "how does a request reach the database" --source. Two calls. The hubs it names are ranked by in-degree, so they really are the important files, not the first ones alphabetically.

How to check it worked: Claude's reply should end with a line like 🌱 graft saved ~24,000 tokens this turn (2 calls). That line is in the skill instructions.

Example 2 — "Where do I add a new field type?"

You:  I want to add a new collection field type. Where do I hook it in,
      and what else has to change?

Claude should run one graft ask "where are collection field types registered" --source. The result comes back with the registry function, its file:line, and the code inline. Then, because you asked what else changes, a graft callers <registry symbol> --depth 2 to find the validators and serialisers that will need the new case.

This is the pattern that showed up as the biggest correctness win in Graft's own SWE-bench run: a cold agent patches one file and misses its siblings. The callers --depth step is what finds the siblings.

Example 3 — Before a rename

You:  Rename `contentHash` to `hashContent` everywhere.

The right first move is graft callers contentHash --depth 2, which is the output shown above: 12 direct callers across 12 files, plus the transitive ones. Now the rename is a checklist, not a search-and-hope. Compare with a raw grep -rn contentHash, which also matches the string in comments, in docs, and in an unrelated variable name — and misses nothing, but tells you nothing about which hits are calls.

Prompt that works well: "Before you change anything, run graft callers <symbol> --depth all and show me the list. Then we decide the scope together."

Example 4 — Multi-file refactor

You:  Split the settings merge logic out of settings-merge.ts into its own
      module. Use `graft callers --depth all` first so we do not miss a file.

--depth all gives the entire connected closure — every file reachable through the edges. That is deliberately wider than --depth 2. It is the mode for "I am about to move code between files and I need to know every import that will break".

Example 5 — Exhaustive audit

You:  Find every place we read an environment variable, and list which ones
      have no default.

This is a grep task, not an ask task, because "every place" rules out ranked top-N. Claude should run graft grep "process\.env\." once. The output groups hits by function and ranks them, so the ones in a hot path float to the top of the list you then review.

Failure mode to watch for: if Claude greps an over-specific pattern — a full guessed signature like func (s *Server) GenerateHandler — it gets zero hits even though the code is there. The fix in the skill is: loosen the pattern to the bare name and retry graft grep, do not fall back to grep -rn.

Example 6 — Reading a file you are about to edit

You:  What can I call from src/claude/hooks.ts? Do not read the whole file.

graft skeleton src/claude/hooks.ts. Roughly a tenth of the tokens of reading it. Then Claude opens only the one function it actually needs to change.

Example 7 — Debugging

You:  Realtime subscriptions stop delivering events after a while.
      Where would you start looking, and why?

Two calls: graft ask "realtime subscription delivery" --source to find the suspect, then graft callers <suspect> to see who drives it and where the lifecycle is managed. The skill explicitly budgets this one at 1–2 calls.

Example 8 — Reviewing someone else's diff

You:  Here is the diff on this branch. What is the risk, and what should
      I test?

Run graft blast --base origin/main. It takes the changed lines, walks the edges out from them, and tells you what areas the change can reach. Add --format markdown to get something you can paste as a PR comment, with per-symbol detail collapsed underneath. By default it also reads Git history to name the people behind each area, which you can turn off with --no-owners.

Example 9 — Working in one package of a monorepo

You:  In the api package only: where is rate limiting enforced?

graft ask "where is rate limiting enforced" --in api/. Without --in, Graft still ranks each sub-project separately and fuses the results — so a huge package cannot drown a small one — and every hit carries a [scope/] label. With --in, you skip straight to the package you care about.

Example 10 — Explicitly asking for the map

Sometimes you want to force it. All of these work as plain instructions:

  • "Use graft, do not grep."
  • "Run graft map first and show me the hubs before you touch anything."
  • "Answer from graft ask --source only. If the crux is truncated, then open the file at that exact range, nothing wider."
  • "Give me the graft token savings for this turn."

7. Blast radius, viz, monorepos

graft blast — the risk of a diff

graft blast                              # working tree vs HEAD
graft blast --base origin/main           # what a PR job would run
graft blast --base origin/main --format markdown   # paste into a PR comment
graft blast --depth all --format json    # full transitive closure, machine-readable
graft blast --export-viz site/           # an interactive page for this radius
graft blast --no-owners                  # skip "who to tag"

There is also a GitHub Action in the repo (.github/actions/graft-blast) if you want this posted automatically on pull requests.

graft viz — look at the graph

graft viz                       # serves an interactive viewer on localhost
graft viz --port 5000 --no-open
graft viz --export site/ --title "PR #12"   # one self-contained index.html

Three tabs: Context (the markdown concept graph), Code (the per-symbol wiring graph), Outline (file → class → method as a collapsible tree). Select a node and the edges take on direction — amber is what it depends on, teal is what depends on it — with the verb written on each edge. Edges extracted by the parser draw solid; LLM-inferred ones draw dashed. The viewer live-reloads when graft/ changes on disk.

Repo layouts it handles

  • Monorepo with one .git — each sub-project is discovered as a ranking scope and ranked on its own terms, then fused.
  • Superproject with submodules — excluded by default. graft build --follow-submodules folds initialised ones in; the choice is saved in .graft/config.json.
  • Repos cloned inside a repo (no gitlink — what west, repo, gclient produce) — graft build --follow-nested-repos. Independent of the submodule flag.
  • A folder of separate repos, no .git at the top — auto-splits. Each child gets its own graft/, the parent gets a graft/workspace.json index, queries from the parent federate across children. graft init at the parent wires every child too, because a session opens at a repo root and reads its instruction files from there.

Commands also find the graph from a subdirectory — with no [dir] argument they walk up to the nearest graft/.

8. Gotchas and how to undo it

1. The project statusline hides your global one. Covered above. Use --no-statusline if you have a custom one in ~/.claude/settings.json.
2. Selecting the agents host writes outside the repo. If ~/.codex/ exists, graft init registers the MCP server in ~/.codex/config.toml, writes ~/.codex/hooks/graft/graft-hooks.cjs, and adds a PostToolUse entry to ~/.codex/hooks.json. Those are user-level: they fire in every repo you open with Codex. You have Codex installed, so this matters. Avoid it with --agents claude (which is what this guide uses throughout) or --no-global.
3. --deep never runs by itself. Auto-sync, the hooks, and every query are structural and free. If you want the LLM concept nodes you must run graft build --deep yourself, with a key. That is a good default, but it means graft check will keep reporting "meaning tier 0% complete" and that is not an error.
4. Never pipe graft through head, tail, or sed -n. Every command is already capped and states what it dropped. Clipping it costs you hits you asked for, and it silently drops the savings line the statusline's running total is parsed from.
5. After you upgrade, graft init will start writing to ~/.claude. In the installed version, 0.16.0, everything graft init writes for Claude Code lands inside the repo. Version 0.17.0 is on GitHub but not yet on npm, and it adds a user-level install: ~/.claude/helpers/graft-hooks.cjs, hook blocks in ~/.claude/settings.json, and mcpServers.graft in ~/.claude.json (the user MCP scope). Those apply to every project you open with Claude Code. It exists for a real reason — a Git worktree checks out tracked files only, so a worktree of a wired repo can end up with the shims present and nothing pointing at them. But it is a behaviour change. So after graft upgrade, run graft init --dry-run once and look for a section labelled global or machine-wide. --no-global suppresses it: in src/claude/init.ts the user-level install is guarded by exactly that flag.
6. The markdown cards can lag by one turn. The six tools always refresh before answering. But if Claude greps the markdown under graft/ directly, those cards are a projection rebuilt at the end of a turn — so after an edit their line spans can be one turn stale. Use the tools, not the raw files.
Telemetry. Already off on this machine. For reference: the only network calls Graft makes are the LLM requests you configured, a daily npm version check, and one batched usage ping carrying buckets and fixed labels — never code, paths, repo names, symbols, queries, or error messages. graft telemetry debug prints exactly what would be sent. Off switches: graft telemetry disable, DO_NOT_TRACK=1, unchecking the box in graft init. It is off in CI and in any build from source.

Undoing it

graft uninstall            # prints what it would remove, removes nothing
graft uninstall -y         # actually remove every file and config entry it wrote
graft uninstall --keep-cache   # wiring only; leave graft/ and the .gitignore line
graft uninstall --no-global    # leave ~/.codex and ~/.gemini alone

And to remove the CLI itself: npm uninstall -g @nanonets/graft.

Keeping it current

graft version    # installed vs latest published
graft upgrade    # npm install -g the latest

A new version is announced automatically, checked once a day. After upgrading, the next session refreshes the repo's wiring by itself.

9. The benchmark numbers

These are the vendor's own measurements, published in their README. They are detailed and the method is described, which is more than most tools offer — but nobody independent has reproduced them. Read them as a claim with evidence attached, not as a settled fact.

Their controlled sweep — 162 runs, two repos, three trials each, Claude Sonnet 5 on both arms, an Opus 4.8 judge with a required-keyword floor so a fast-but-wrong answer could not win:

Mean per taskCold Claude CodeWith Graft
Cost$0.0429$0.0292 (−32%)
Tokens8,0704,650 (−42%)
Tool calls4.22.3 (−46%)
Latency39.8s15.8s (−60%)

10. What to do next

  1. Pick one real repo — something with enough files that you actually get lost in it.
  2. cd into it and run graft init --dry-run --agents claude. Read the five lines it prints.
  3. If you run a custom statusline, add --no-statusline.
  4. Run it for real: graft init --agents claude. Then restart Claude Code so the MCP server loads.
  5. Commit the wiring: git add .claude .mcp.json && git commit -m "wire in graft". Do not commit graft/ — it added itself to .gitignore.
  6. Ask a question you already know the answer to, and watch whether Claude reaches for graft ask instead of grepping. That is the test of whether the wiring took.
  7. Optional, costs money: set GRAFT_PROVIDER / GRAFT_API_KEY / GRAFT_MODEL and run graft build --deep to add the plain-English concept nodes.
