Graft in practice

Five requests against one real Rust codebase. Three needed no code index at all. Two did. This page shows every request and reply as they happened, and explains the difference.

Session of 8 September 2026 · graft 0.16.0 · repository larql_copy — 1,482 files, 21,581 symbols, 32,435 edges · companion to graft-guide.html

What graft is, in plain words

Graft reads a repository once and writes down what it found: every function and type, where each one is defined, and which ones call which. That record is the graph. Afterwards you ask questions of the graph instead of opening files.

The point is not speed. The point is that an answer arrives as a short list of exact locations rather than as thousands of lines you then have to read. Here is how graft describes itself.

Usage: graft [options] [command]

Build a repo's context graph as linked markdown, and keep it in sync with the
code.

Commands:
  build [options] [dir]             Build graft/ from your code - wiring graph +
                                    per-file cards ($0, no key).
  ask [options] <query> [dir]       Query the graft/ graph - returns ranked
                                    nodes + exact file:line ($0, no key)
  skeleton [options] <file> [dir]   Signatures-only view of one file from the
                                    wiring graph - the cheapest way to see a
                                    file's API surface
  callers [options] <symbol> [dir]  Who calls/references a symbol ($0, no LLM).
  grep [options] <pattern> [dir]    Regex search over indexed files, hits
                                    grouped by enclosing symbol and ranked by
                                    coupling ($0, no LLM)
  map [options] [dir]               Token-budgeted repo orientation - directory
                                    clusters, per-directory hubs, and global
                                    hotspots from the wiring graph ($0, no LLM)

Four commands did all the work in this session. None of them uses a language model, needs an API key, or touches the network.

CommandQuestion it answers
graft callers <symbol>Who calls or references this thing?
graft grep <pattern>Where does this text appear — and which function is it inside?
graft skeleton <file>What is this file's API surface, without the bodies?
graft mapWhere is this repository big and busy?

The one rule that decides everything

Graft indexes code. It does not index prose or configuration.

Markdown files, README files and Cargo.toml manifests are invisible to the graph. In larql that is 252 markdown files and 17 manifests — and it happens to be where the architecture is written down.

So the question to ask before reaching for graft is not “is this about the codebase?” It is “does the answer live in the code, or in the words about the code?” Every verdict on this page follows from that one distinction.

User request 1

can you create an ascii diagram showing the architecture of larql

Graft not used

The answer lived in prose and in config files. Graft indexes neither.

Why not

Three pieces of information were needed. Graft could supply none of them.

  1. What each crate is for. This is written in larql/docs/onboarding/architecture.md — a markdown file. Graft builds its graph from code. It parses functions, types and call sites. It does not read prose. The larql repository holds 252 markdown files and every one of them is invisible to the graph.
  2. Which crate depends on which. This is declared in the 17 Cargo.toml manifests. A manifest is configuration, not code. Graft has no edge type that means “crate A lists crate B in its dependencies”.
  3. What a vindex looks like on disk. Another markdown file.

Four notes, then one offer:

  1. The doc chain is wrong in two places. docs/onboarding/architecture.md puts larql-vindex above larql-inference, and larql-inference above larql-kv. The real build edges run the other way: larql-inference depends on larql-vindex, and larql-kv depends on larql-inference. The reverse edges exist, but only as [dev-dependencies]. My diagram uses the build edges.
  2. The diagram draws the shortest path only. Most crates also depend directly on lower tiers. Example: larql-cli depends on 8 crates — compute, compute-metal, core, inference, kv, lql, models, vindex.
  3. Crate count. The Cargo workspace has 16 members. larql-experts is a 17th crate directory with its own Cargo.lock and its own workspace. No workspace crate imports model-compute or larql-experts today.
  4. Not drawn: the three data flows (DESCRIBE, INFER, INSERT→COMPILE). Say the word and I will draw them as a second diagram.

The decision rule

Five exchanges are enough to state the rule plainly.

Reach for graft when…Read the file instead when…
The question names a symbol — a function, type, or trait. The question is about intent, design, or why something exists.
You want edges: callers, callees, blast radius. The answer is in a README, a design doc, or an ADR.
You want a file's shape without its contents. The answer is in a manifest, a lockfile, or any config.
The honest alternative is opening many files to find a few lines. You already know the one file and the one line.

Five practical lessons

  1. A failed graft command can be the most useful one. graft callers KvDispatch returned nothing, but it named the symbol an interface. That one word reshaped the whole answer.
  2. Use symbol names with callers, not regular expressions with grep. Three regex searches returned nothing on names that callers resolved immediately.
  3. graft grep takes a regex, so punctuation bites. A leading + is a syntax error, not a search term.
  4. Text hits are not call sites. Of 102 hits for KvDispatch, most were doc comments and re-export lines. The graph finds the text; a person still decides what it means.
  5. Graft reports its own blind spots. It warned that two functions share the name read_kv_row_at and that it drops ambiguous edges rather than guessing. Pass that warning on rather than hiding it.
